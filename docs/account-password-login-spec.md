# Аккаунт клиента: вход по паролю и заполнение профиля

**Статус:** draft
**Дата:** 2026-11-13
**Проект:** shop-web (Next.js 16, React 19, App Router)

---

## 1. Проблема и цель

Сейчас клиент попадает в аккаунт только по коду из SMS. При первом входе на новый номер создаётся пользователь, у которого есть только `phone`. Имени, почты, аватара и пароля нет.

Нужно:

1. Оставить регистрацию/вход по SMS как основной и единственный способ создать аккаунт.
2. Дать пользователю возможность добровольно заполнить профиль: имя, почту, аватар.
3. Дать возможность установить пароль и входить по нему без SMS.
4. Не допустить создания аккаунта на чужой номер: аккаунт создаётся только после подтверждения кода из SMS.
5. Показывать пользователю, что профиль не заполнен (имя/пароль), и вести его в настройки.

**Главный принцип:** `1 телефон === 1 аккаунт`. Телефон — неизменяемый идентификатор. Пароль — вторичный, необязательный способ входа.

## 4. Целевое состояние

### 4.1. Состояния пользователя

| Состояние | `phone` | `name` | `email` | `avatar_url` | `has_password` | Что показываем |
| --- | --- | --- | --- | --- | --- | --- |
| Гость | — | — | — | — | — | «Войти» в шапке |
| Новый (после SMS) | + | null | null | null | false | Бейдж `!`, уведомление на `/profile` |
| Частично заполнен | + | + | null | null | false | Бейдж `!` (нет пароля) |
| Частично заполнен | + | null | + | + | true | Бейдж `!` (нет имени) |
| Заполнен | + | + | null | null | true | Без бейджа, без уведомления |

Почта и аватар **не влияют** на бейдж и уведомление. Достаточно имени и пароля.

### 4.2. Пользовательские сценарии

#### A. Первая регистрация по SMS

1. Гость открывает `/sign-in`, вводит телефон.
2. Нажимает «Получить код» (кнопка доступна только при `canSendSms === true`).
3. Вводит код из SMS.
4. Бекенд создаёт пользователя с одним полем `phone` (если номера не было) и выдаёт токены.
5. Пользователь попадает на `/profile`, в шапке — иконка с `!`.
6. На `/profile` — уведомление «Заполните профиль» и ссылка в `/profile/settings`.

#### B. Заполнение профиля

1. Пользователь открывает `/profile/settings`.
2. Заполняет имя/почту, загружает аватар, при желании устанавливает пароль.
3. Телефон отображается только для чтения.
4. После сохранения — тост, обновление данных, бейдж исчезает, если имя и пароль заданы.

#### C. Вход по паролю

1. Пользователь открывает `/sign-in`, вводит телефон.
2. Нажимает «Войти по паролю».
3. Фронтенд запрашивает `auth/check-password`.
4. Если пользователь есть и пароль установлен — показывается поле пароля.
5. Ввод пароля → `auth/login-by-password` → токены → переход назад/в профиль.
6. Если пароля нет или пользователя нет — сообщение от бекенда (или fallback) и предложение войти по SMS, если SMS доступно.

#### D. SMS недоступно

1. `canSendSms === false`.
2. На `/sign-in` показываем общее уведомление о недоступности SMS.
3. Кнопки отправки кода скрыты.
4. Вход по паролю остаётся доступным.
5. Если пароль не подходит/не установлен/пользователя нет — показываем общую ошибку: SMS недоступно и войти по паролю нельзя.

## 5. Модель данных (бекенд)

Таблица `users` (уточнить фактическое имя в БД):

| Поле | Тип | Обязательность | Комментарий |
| --- | --- | --- | --- |
| `id` | int/bigint | да | PK |
| `phone` | varchar(11) | да, unique | Нормализованный номер `7XXXXXXXXXX`, immutable |
| `name` | varchar(50) | нет | null, если не задано |
| `email` | varchar(255) | нет | null, если не задано; валидный email при наличии |
| `avatar_url` | text | нет | URL загруженного изображения |
| `password_hash` | text | нет | null = пароль не установлен; argon2id/bcrypt |
| `password_set_at` | timestamptz | нет | Для аудита, опционально |
| `role` | varchar | да | Существующее поле |
| `created_at` | timestamptz | да | Существующее поле |
| `updated_at` | timestamptz | да | Существующее поле |

Требования:

- `UNIQUE INDEX users_phone_unique ON users(phone)`.
- `password_hash` никогда не отдаётся наружу.
- `auth/verify-otp` при существующем пользователе **не перезаписывает** `name`, `email`, `avatar_url`, `password_hash`.
- При создании нового пользователя через OTP заполняется только `phone` и системные поля.
- Пароль хранится только в виде хеша; сравнение — constant-time.

## 6. API

### 6.1. Существующие ручки

| Метод | URL | Назначение |
| --- | --- | --- |
| POST | `sms/request-otp` | Отправить код. Тело: `{ phone, device_id, hash_code }` |
| POST | `auth/verify-otp` | Проверить код, создать пользователя при необходимости, выдать токены. Тело: `{ phone, code }` |
| GET | `sms/can-send-sms` | `true \| false \| null` — доступна ли отправка SMS |
| GET | `users/me` | Текущий пользователь |
| POST | `auth/refresh-token` | Обновление токенов |
| POST | `auth/logout` | Выход |

### 6.2. Расширение `GET users/me`

`data`:

```ts
type UserModel = {
  id: number;
  phone: string;
  name: string | null;
  email: string | null;
  avatar_url: string | null;
  role: string;
  has_password: boolean;
};
```

`has_password` вычисляется на бекенде как `password_hash IS NOT NULL`. Хеш не возвращается.

**Текущее состояние фронтенда:** в `UserModel` уже добавлен `has_password` (`src/app/action.ts:20`). Поля `name` и `email` описаны как `optional`, а не `nullable`, и `avatar_url` ещё не добавлен — это нужно привести к контракту выше. Zod-схема `userSchema` объявлена, но не применяется к ответу `users/me`; запрос типизируется через `fetchService.get<UserModel>` без runtime-валидации.

### 6.3. `PATCH users/me` — личные данные

Запрос:

```json
{
  "name": "Иван",
  "email": "ivan@example.com",
  "avatar_url": "https://cdn.example.com/avatars/1.webp"
}
```

- Все поля опциональны.
- Пустая строка приводится к `null`.
- `phone` в теле запрещён: вернуть `400` с сообщением.
- `name`: 2–50 символов после trim, либо `null`.
- `email`: валидный email либо `null`. Уникальность — см. открытые вопросы.
- `avatar_url`: только URL, полученный от `POST users/me/avatar`, либо `null`.
- Ответ: `ResponseData<UserModel>`.

### 6.4. `POST users/me/avatar` — загрузка аватара

- `multipart/form-data`, поле `file`.
- Допустимые типы: `image/jpeg`, `image/png`, `image/webp`.
- Максимум 5 МБ.
- Ответ: `ResponseData<{ url: string }>`.
- Старый файл удаляется/перезаписывается на стороне бекенда.

> Если на бекенде уже есть общий загрузчик файлов — использовать его, а этот контракт считать адаптером.

### 6.5. `PUT users/me/password` — установка/смена пароля

Запрос:

```json
{
  "password": "new-password",
  "repeat_password": "new-password",
  "current_password": "old-password"
}
```

Правила:

- `password`: 6–50 символов.
- `repeat_password` должен совпадать с `password`.
- Если пароль ещё не установлен — `current_password` не требуется.
- Если пароль уже установлен — `current_password` обязателен и проверяется.
- Ответ: `ResponseData<{ has_password: true }>`.
- Ошибки: `400` валидация, `401` не авторизован, `403`/`400` неверный текущий пароль.

### 6.6. `POST auth/check-password` — можно ли войти по паролю

Запрос:

```json
{ "phone": "79493865786" }
```

Ответ (200):

```json
{
  "data": { "exists": true, "has_password": true },
  "status": "success",
  "message": "",
  "errors": [],
  "tokens": null
}
```

Правила:

- Возвращать `exists: false` и `has_password: false` без ошибки, если номера нет (не раскрываем лишнего ошибкой).
- Rate limit по телефону и IP: например, 5 запросов в минуту. При превышении — `429` с `message`.
- Не возвращать никаких других данных пользователя.

### 6.7. `POST auth/login-by-password` — вход по паролю

Запрос:

```json
{ "phone": "79493865786", "password": "secret" }
```

Ответ (200): токены как у `auth/verify-otp`:

```json
{
  "data": { "token": "...", "refresh": "..." },
  "status": "success",
  "message": "",
  "errors": [],
  "tokens": null
}
```

Ошибки:

- `401` — «Неверный пароль».
- `404` — «Пользователь с таким номером не найден».
- `429` — «Слишком много попыток. Попробуйте позже».
- Тексты приходят в `message` и показываются на фронтенде без изменений.

### 6.8. Временная заглушка фронтенда

Пока ручек `auth/check-password` и `auth/login-by-password` нет:

- `checkPasswordAction` возвращает `success` с `{ exists: true, has_password: true }`.
- `loginByPasswordAction` возвращает `error` с сообщением «Вход по паролю пока не подключён».
- Обе функции помечаются `// TODO(backend)` и меняются на реальные запросы в одной точке (`src/app/sign-in/action.ts`).

### Задача 2. Вход по паролю на `/sign-in`

**Цель:** дать быстрый вход без SMS, не убирая вход по коду.

**Затрагиваемые файлы:**

- `src/app/sign-in/page.tsx`
- `src/app/sign-in/action.ts`
- `src/app/sign-in/schema.ts`
- `src/app/sign-in/signin-form/SigninForm.tsx`
- `src/app/sign-in/signin-form/SigninForm.module.css`

**Состояния формы:**

```ts
type AuthMode = "phone" | "sms-code" | "password";
```

| Поле | Назначение |
| --- | --- |
| `mode` | Текущий шаг |
| `phone` | Введённый номер |
| `validPhone` | Результат zod-валидации |
| `hasPasswordForPhone` | Ответ `auth/check-password` |
| `password` | Введённый пароль |
| `isCheckingPassword` | Идёт проверка номера |
| `canSendSms` | Проп из `page.tsx` |

**Логика:**

1. Шаг `phone`:
   - кнопка «Получить код» видна и активна только при `canSendSms && validPhone && !isLoading`;
   - кнопка «Войти по паролю» видна всегда, активна при `validPhone && !isCheckingPassword`;
   - при изменении телефона сбрасываются `mode = "phone"`, пароль, ошибки и `hasPasswordForPhone`.
2. Нажатие «Войти по паролю»:
   - вызывает `checkPasswordAction(phone)`;
   - `success && data.exists && data.has_password` → `mode = "password"`, показываем поле пароля;
   - иначе — показываем `response.message`; если сообщения нет — fallback «Для этого номера не настроен вход по паролю. Войдите по коду из SMS» (при `canSendSms === true`);
   - при `canSendSms === false` — общая ошибка из задачи 3.
3. Шаг `password`:
   - поле «Пароль» (`type="password"`, `autoComplete="current-password"`);
   - кнопка «Войти»;
   - submit → `loginByPasswordAction(phone, password)`;
   - успех: сохранить токены (куки), `router.back()` / `router.push("/profile")`;
   - ошибка: показать `response.message` дословно, не очищая телефон;
   - ссылка «Войти по коду из SMS» (если `canSendSms`) → сброс в шаг `phone` и сразу отправка кода, либо возврат к кнопке «Получить код». Выбрать один вариант и зафиксировать в реализации; рекомендуется сразу отправлять код.
4. Шаг `sms-code` — существующее поведение без изменений.
5. Ошибки:
   - приоритет: `response.message` от бекенда → fallback → общий текст;
   - ошибка одной строкой под полями, `aria-live="polite"`;
   - при смене телефона/пароля ошибка очищается.

**Критерии приёмки:**

- Ввод корректного телефона активирует «Войти по паролю».
- Для пользователя с паролем появляется поле пароля.
- Верный пароль пускает в аккаунт без SMS.
- Неверный пароль показывает сообщение бекенда.
- Для номера без пароля показывается сообщение и остаётся возможность получить SMS.
- SMS-вход продолжает работать как раньше.
- Вход по паролю работает при `canSendSms === false`.
- Телефон меняется — пароль и ошибки сбрасываются.

**Зависимости:** задача 0 (ручки) или заглушка из п. 6.8.

### Задача 3. Логика `canSendSms` на `/sign-in`

**Цель:** корректно объяснить пользователю, почему он не может войти, если SMS недоступно.

**Подзадачи:**

1. Прокинуть `canSendSms` из `page.tsx` в `SigninForm` пропом.
2. Если `canSendSms === false`:
   - показывать общее уведомление (не ошибку конкретного поля): «Сервис SMS временно недоступен. Вход по коду сейчас невозможен»;
   - скрывать кнопку «Получить код»;
   - не запускать таймер повторной отправки и не показывать «Отправить код ещё раз»;
   - не показывать шаг ввода кода;
   - оставить кнопку «Войти по паролю» и поле пароля.
3. Если вход по паролю невозможен (`exists === false` или `has_password === false`) и `canSendSms === false`, показывать **одну общую ошибку**:
   > «Сервис SMS временно недоступен, а для этого номера не настроен вход по паролю. Попробуйте позже.»
   Если бекенд вернул свой `message` — показывать его, но не дублировать оба текста.
4. Если `canSendSms === true` — поведение как в задаче 2, отдельного уведомления нет.
5. Если `canSendSms === null` (ошибка запроса) — трактовать как `false`, чтобы не показывать неработающую кнопку SMS.
6. Учесть, что после успешного входа по паролю `canSendSms` не важен.

**Критерии приёмки:**

- При `false` нет кнопок отправки SMS.
- Вход по паролю остаётся доступным.
- Невозможность входа объясняется одним понятным сообщением.
- Нет визуального дублирования ошибок.
- При `true` и `null` поведение предсказуемо и описано тестами/чек-листом.

**Зависимости:** задача 2.

## 8. Краевые случаи

| Ситуация | Поведение |
| --- | --- |
| Новый номер, SMS доступно | OTP создаёт аккаунт только с телефоном |
| Новый номер, SMS недоступно | Войти нельзя; общая ошибка |
| Номер есть, пароля нет, SMS доступно | Предложение получить код |
| Номер есть, пароля нет, SMS недоступно | Войти нельзя; общая ошибка |
| Номер есть, пароль есть, SMS недоступно | Вход по паролю работает |
| Неверный пароль | Сообщение бекенда, поле не очищается |
| Пользователь меняет телефон после открытия поля пароля | Режим сбрасывается на ввод телефона |
| Пользователь очистил имя | `name = null`, бейдж появляется снова |
| Пользователь удалил аватар | `avatar_url = null`, бейдж не появляется |
| Ошибка загрузки аватара | Старый аватар сохраняется, показывается ошибка |
| Два запроса на регистрацию одного номера | Уникальный индекс, второй запрос получает ошибку |
| Пользователь не авторизован на `/profile/settings` | `NotContent`/редирект на `/sign-in` |
| Бекенд вернул пустой `message` | Использовать fallback-текст |

## 10. Безопасность

1. Аккаунт создаётся только после успешного `auth/verify-otp`.
2. Телефон неизменяем: `PATCH users/me` игнорирует/отклоняет `phone`.
3. Пароль хранится только как argon2id/bcrypt-хеш.
4. Rate limit:
   - `auth/check-password`: 5 запросов/мин на телефон + IP;
   - `auth/login-by-password`: 5–10 попыток/мин, затем `429`;
   - OTP: существующие лимиты.
5. Ответы не раскрывают `password_hash`, `id` других пользователей и лишние данные.
6. Не логировать пароли и коды.
7. Смена пароля в авторизованной сессии требует текущий пароль.
8. При компрометации пароля пользователь всегда может войти по SMS и сменить пароль.
9. CSRF: server actions Next.js; для API — существующая схема токенов.
10. Загружаемые аватары: проверка MIME и размера, хранение вне публичного исполняемого контекста.
